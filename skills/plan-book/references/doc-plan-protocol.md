# doc-plan-protocol — 文档态计划协议

**定位**：V11/V12 计划线共五件 —— `plan-template`（生成机器态计划）/ `plan-executor`（执行）/ `introspect-guard`（逐步硬校验）/ `execution-log`（日志）/ `plan-auditor`（审计）。
**五件全为机器态**，而真实大任务常以**文档形态**立项（任务书、方案书、分批执行计划）⇒ 那一段**无规程可依**，实测四要素覆盖率 **0/4**。
**本技能补的就是这一段**：文档态计划的"怎么写、怎么冻结、怎么推进、怎么验收、怎么回流"。

> 归属：类大脑模式 · **计划层（前额叶皮质）** —— "先设计步骤、风险、验证点"。
> 治理依据：`outputs/2026-08/计划推进验证协议-v1.0-2026-08-14.md` + `outputs/2026-09/计划推进验证协议-v1.1-增量修订-20260924.md`

---

## 零、门槛触发（🔴 先判该不该走本规程 —— 禁止无脑套用）

| 情形 | 走法 |
|:--|:--|
| 单步任务 / 纯只读查询 / 即问即答 | ❌ **豁免**，直接做（协议 §四 豁免条款） |
| 3~8 步、**单会话内可完成**、产出不需长期回溯 | 🟡 用 `plan-template` 生成 **JSON/MetaSkill 轻量计划**，**不写任务书** |
| **≥3 步 且（跨会话 / 跨日 / 产出需长期可回溯 / 涉批量外部文档）** | ✅ **走本规程**（文档态任务书） |

**判据**：问一句 —— 「**这个任务中断一天后，另一个人能靠这份文档接着跑吗？**」能 ⇒ 文档态；不能 ⇒ 轻量计划。

## 一、六步流程

```
S1 打靶评估 ──→ S2 四要素任务书 ──→ S3 冻结 + 追加式执行记录
                                        │
                                        ↓
        S6 复盘回流 ←── S5 总门禁 ←── S4 逐批门禁
```

### S1 · 打靶评估（**唯一的"事前防线"**）

把方案的每个前提写成**可证伪命题**，用真实文件系统/真实数据逐条实测，**不推演**。产出 `方案评估报告-<日期>.md`，必含：

- **假设打靶表**：`假设 | 实测结果 | 判决（🟢成立 / 🔴推翻 / 🟡有条件 / ⚪未验证）`
- **遗漏清单**（P0 不改则白做 / P1 应改 / P2 建议）
- **诚实性声明**：逐个列出**未做的验证**，并标"这是可能翻转项"

> 🔴 **铁律**：**"未验证"不得升级为"建议/结论"**。
> 反面实证：某内部项目 评估报告 §8 已诚实标注「`.doc` COM 转换链**未实测**，是唯一残留的"可能翻转"项」，
> 而任务书把它升级为「**必须装 LibreOffice**」+ 🟠 高 + B2 前置动作 ⇒ 后被零依赖方案全盘推翻，白绕一轮。

### S2 · 四要素任务书

文档态**不强制改 YAML**，但每批必须**可机械提取**四要素：

| 要素 | 文档态写法 | 禁 |
|:--|:--|:--|
| 前置依赖 | 每批一行 `依赖：B0,B1`；或文首依赖图（ID 须与批次表逐字一致） | 只写散文箭头 |
| 可并行 | `可并行：<ID 列表>`，无则 `—`（**禁止留空**） | 只写"可任意时点插入" |
| 完成判定 | `完成判定：<文件路径 + 客观读数（阈值/退码/计数）>` | 「完成了」「80%」等主观自评 |
| **推进门禁** | `门禁：<不满足时的动作>`，默认**「回退修补 1 次 → 仍失败 → 挂起待人工确认」** | **留空**（= 无门禁，本规程头号反模式） |

🔴 **受理判据（可机械执行）**：对批次表逐行提取 `依赖：`/`可并行：`/`完成判定：`/`门禁：` 四键 —— **任一键在任一行缺失 = 不通过，不予受理**。

#### 🆕 §S2-a · 判据上线前置扫描（**2026-09-24 新增 · 硬要求**）

🔴 **凡本任务新增任何判据（检查项 / 判定阈值 / 完成判定 / 门禁条件），必须先跑下面 3 问 + 1 兜底，并把结论写入执行记录。**

| # | 问 | 若答"是" ⇒ 动作 |
|:-:|:--|:--|
| **J-1** | 我是否**构造了 3 个该判据会误判的反例样本**并实跑过？ | 未做 ⇒ **判据不得上线**（反例样本库见 `declared-value-drift-guard §五·二`） |
| **J-2①** | 我锚的是**本体属性**，还是**一个容易算的代理量**？ | 重选锚（回到"我要证明的那件事是什么"） |
| **J-2②** | 我锚的是**目标状态**，还是**过程状态**（曾经坏过 / 曾经有 FAIL）？ | 一律改锚**目标状态**；过程量降为"过程读数，不作判据" |
| **J-2③** | 判据的**真值来源**是否与我**自己的产物**同源？ | 须引入**外部权威**（字段位锚定 / 独立消费者）—— 自指四形态见 `declared-value-drift-guard §第 3.5 步` |
| **J-2④** | 判据是否显式写明**适用时点 / 前置条件**？ | 补一行「本判据自 YYYY-MM-DD 起才可判读」 |
| **J-3** | 结果是否"**过度整齐**"（恒 0/N、恒 N/N、恰好整数）？ | **先问"这个整齐有没有结构性解释"** —— 有（幂等重跑 / 日期限定）⇒ 正常；无 ⇒ **怀疑判据口径** |
| **J-4** 🆕 | 完成判定锚的是「**被点名对象的数量**」还是「**问题消除判据**」？ | 🆕 **v1.2.2 新增** —— 前者 ⇒ **必须改锚**：凡"**发现类**"结论（如"某漂移/缺陷是**系统性**的"）**不得只按抽样样本数设判据**，须改设「**全量覆盖判据**」（如"全量体检报告在盘"），或**显式声明"本次仅覆盖 N/M"**。<br>🔴 **实测依据**：`某元项目` V12 任务书 B4 —— §二 H9 以「抽 5 处、**2 处**过期」判「漂移**系统性**成立」（外推约 180 处），而 §一 B4 的完成判定只写「**2 处**已修正」⇒ **判据通过但问题仍在**（实测同型断言 **137 文件 / 457 处**，B4 覆盖 **2 处 ≈ 0.4%**）。<br>⚠️ **同族**：反模式 #4「代理变量代本体变量」（用"修了 2 处"代"漂移被治理"）＋ **#13「完成即留尸」**（修完即关门，未留"还有 455 处"的反问） |

> 🔴 **为什么是硬要求**：`某内部项目` 某业务场景构建期 **4 小时内出现 7 例判据缺陷**（虽每例事后都写入执行记录，**下一例照旧发生**）——
> 而**其中 6 例的反例样本"扫一眼就能看见"**（成本近乎 0，收益是全链返工）。**记录 ≠ 拦截，前置扫描才是拦截。**
> 完整 7 例 + 统一根因 + 反例样本库：`某内部项目/outputs/2026-09/7例判据缺陷族系统化-20260924.md`。

**任务书还应带**：
- `§前置假设与证据状态` —— 把 S1 的假设表**带入**（含已证伪项，**禁止删除已证伪项**：它们是"防回退"的唯一凭据）
- `§风险登记册` + `§产出物清单`（每项附**在盘校验**列：文件/大小/mtime）
- **技能栏用「预期 / 备用 / 实际调用」三列** —— 单列"计划用哪些技能"事后无法核对

### S3 · 冻结 + 追加式执行记录

🔴 **计划本体一次发布即冻结，永不就地改写。** 进度写入**独立执行记录**（追加式）：

```markdown
## <批次 ID> · <完成时间>
- 实绩产出：<路径>
- 与计划偏差：<有/无 + 说明>
- 验收读数：<原文读数>
- 门禁：✅通过 / 🔴挂起（原因）
```

> **为什么不能就地打勾**：某内部项目 任务书就地打 ✅ ⇒ ① B7 节重复出现两次（计划版 + 实绩版）② B1~B6/B8 原计划文本被覆盖 ③ **"预判 vs 后知"永久不可审计**。
> **计划不可复盘，等同未评审。**

**升版走新文件**：`任务书-v1.0.md` → `任务书-v1.1.md`（`supersedes` 指向旧版），**v1.0 冻结保留**。

> ✅ **正面实证（2026-09-24 · 某内部项目 某业务场景任务）**：该任务**做到了**计划/实绩分离（执行记录明文"任务书是计划、本文件是实绩，追加式只增不改"），
> 结果：**任务书 v1.0~v1.7 八版全在盘** + **先于执行的预判凭据（§0.5 假设表）原始保留** ⇒ 其 S6 复盘**可直接用原文作判据，无需旁证重建**
> （对照 IK 任务只能改用评估报告作旁证）。**⇒ 这条铁律的收益已可量化：复盘成本从"重建参照系"降为"直接读原文"。**

#### 🆕 §S3-a · 升版零残留对账（**2026-09-24 新增 · 硬要求**）

🔴 **升版 ≠ "复制旧版 + 只改被本次裁决点名的那个行"。** 实测：本做法导致**同一事实的其余副本全部停在旧值**（`某内部项目` 某业务场景任务 **4 小时内 9 处**）。

**强制动作**：产出新版本文件后，**必须 diff 出"未随本次裁决更新的声明"**，对账范围包括：

| 对账对象 | 实测残留例（`某内部项目`） |
|:--|:--|
| **版本号**（正文标题 / frontmatter / 内部引用 / 产出物清单自述） | 任务书 frontmatter `v1.7`，而**正文标题仍写 `v1.1`**、`checklist:` 指 `…-v1.1.md`、产出物清单自称 `v1.1` ⇒ **同一文件 4 处** |
| **可数事实**（检查项数 / 对象数 / 视图数） | 清单 `### 3.1 机器判定 · 57 项`，而**同表表体求和 = 48**；某脚本头部注释仍写 `76 项` |
| **执行顺序图 / 流程图** | 任务书执行顺序图仍写 `B2 视图刷新(13)`，实际 **10** |
| **风险册 / 缓解措施** | 风险册 R2 仍写"**本文件 §1 已推翻的判据**"（§1 已改，§3 未同步） |
| **内部引用目标是否存在**<br>🆕 **v1.2.1 扩范围：含"关联文件"** —— 执行记录／实绩记录中的**批次编号**、frontmatter `plan_ref`、PENDING 指针 | 执行记录 frontmatter `plan_ref → 任务书-v1.1`（实为 v1.7）⇒ **引用悬空**<br>🆕 **实测（某元项目 V12 任务书 v1.1→v1.2 · 2026-09-26）**：执行记录**升版说明区已同步**、**仅"未落地项"表仍写旧编号 `B6`（应为 `B11`）** ⇒ **衰减不对称：越靠下游越旧** |
| **元描述**（标题里的序数词 / 导读） | 清单导读「4 场景 + **9** 项功能 + **4** 项判读」，而正文为 10 项功能 + 3 项判读 |

> 🔴 **判据**：**凡"同一事实"在多处出现的，逐处更新；无机器校验的，登记为待修项。**
> 配套：`declared-value-drift-guard §第 2.5 步`（副本计数校验 `count_copies`）+ `§第 4.5 步`（元描述层对账）。
> ⚠️ **升版只覆盖"计划本体"是不够的** —— 实测 `某内部项目` 的**分析类文档**（清单 v1.0 / 范围界定 v1.0）仍被就地编辑而**丢失原件**（同一失误 **40 分钟内复发 2 次**）。
> ⇒ **升版纪律必须覆盖全部文档类型**（计划本体 + 清单 + 分析件 + 脚本注释 + 🆕 **执行记录／实绩记录**）。

### S3-b · PENDING 登记（🔴 必做 · **登记主旨 ＝ 任务书指引**）

任务书发布后，须回写项目 `memory/PENDING.md`，**新增一节指向任务书**。
🔴 **主旨由用户 2026-09-24 裁决确立**：PENDING 是**入口台账**，不是计划副本。

| 登什么 | 不登什么 |
|:--|:--|
| ① **任务入口 1 条**：ID + 一句话范围（批次链） + **执行窗口** + **机器可判完成标准**（退码/读数）<br>② **未澄清 / 未验证项各 1 条**：拍板人 + **最晚确认时点**<br>③ **台账指针**：任务书 / 检查清单 / 锚点 / 门禁 / 派发报告 的路径 | ❌ **批次明细一律不重复**（B0~Bn 的四要素、产出清单、检查项明细）—— **以任务书为准** |

🔴 **为什么（根因）**：批次表若**同时存在于任务书与 PENDING**，即**同一事实被声明在两处 ⇒ 必然漂移**（§二 反模式 #4「判据先于事实」同型）。
PENDING 只该回答「**有没有这件事 / 找谁 / 什么时候要**」，**不回答「怎么干」**。
✅ 正例：`PENDING.md §「9/30 晚间某业务场景配置与功能检查任务」`（SYBX-01 入口 + AI-105~112 未澄清项；节首明文「本表只登记任务入口与未澄清项，B0~B9 明细不在本表重复」）。
❌ 反例（IK 任务 v1.0 曾犯）：把批次表复制进 PENDING ⇒ 两处声明漂移；且 PENDING 被就地改写后**无从判别"预判 vs 后知"**。

🔴 **最晚确认时点必填**：未验证项若只写「拍板人」不写「时点」，**必然拖到执行当日才发现**。
实证：某内部项目 某业务场景任务（9/24 立项 → 9/30 执行）中，**4.0 控件适用组**（三组 DDL 内容各不相同，选错即白改）与 **M1 口径**（出院字段真实值 vs 默认值）若拖到 9/30 当晚，**当晚无法补救** ⇒ 已定「**最晚确认 9/28**」（留 2 天缓冲）。

### S4 · 逐批门禁（事中验证）

每批结束：

```
① 依赖验证：depends_on 全部 gate 通过？未满足 → 阻塞（标 blocked_by）
② 完成判定硬校验：对照 done_when 客观校验（重新实测，禁文字沿用）
     ├─ 通过 → 记录 gate=✅ → 推进下一批
     └─ 不通过 → 回退修补 1 次 → 重执行
           └─ 仍失败 → 标记 gate=🔴 挂起待人工确认（不静默跳过）
③ 写入执行记录（S3 格式）
```

🔴 **"窗口已过" ≠ "已完成"** —— 时间窗口过了不等于事情做了，归档时须标 `❓ 待人工确认`，**不得据"归档动作"推断完成**。

#### 🆕 §S4-a · 判断权不归执行者（**2026-09-26 新增 · 源起 `任务书 v1.3` §一 B6**）

> 执行者在 S4 逐批门禁中 **不得自行宣布「不必升档」或「不必审计」**（`AGENTS.md`「🔑 权限分级」节亦载同条 —— **两处载体，同一事实**）。
>
> | # | 禁止形态 | 反例句式（命中即违） |
> |:-:|:--|:--|
> | ① | **自行降档** —— 把自己判定为**低于判据给出的档位**（例：A2 事项按 A0 执行） | 「这属小事，直接做」 |
> | ② | **自行豁免审计** —— 宣称某动作「不涉规范／不涉治理文件／无风险」从而跳过批红或门禁 | 「这个不涉治理文件，不用批」 |
> | ③ | **自行宣布"不必审计"** —— 对本应触发的门禁/审计项宣告「**可省**」 | 「我判断这事不用上会」 |
>
> **判定权归属**：档位与"是否审计"的判定权**不归执行者** —— 由 ① `权限分级规范-2026-09-26.md` **边界清单**（机器可判）② `tools/gate_chain.py` **门禁链** ③ **用户**，三方之一给出。
> 🔴 **门禁为 BLOCKING 时，执行者无"自行判定可省"的权限** —— 只能 ① **照做** ② **挂起并报明原因**（对应 S4 的 `gate=🔴 挂起待人工确认`）。
> 📌 **本条不新造机制**：仅把既有的「边界清单 ⇒ A2 起」与「BLOCKING 门禁」**显式化为对执行者的禁令**，防"**以判断代判据**"。

#### 🆕 §S4-b · 门禁措辞须显式区分「**首判**」与「**反转**」（**2026-09-26 新增 · 源起 `某元项目` V12-CLEANUP B10**）

> **判据**：门禁条件里出现「**反转**」时，**其含义限于「已有判决被推翻」**；**首次判决不构成反转**。
> **属主**：本条是**协议层**规则（讲「**计划判据怎么读**」），**不属**任何 SSOT / 领域文档的内容 —— 混入后者即制造**第二个同源判据**。

**实证（2026-09-26）**：`某元项目` V12-CLEANUP **B10 门禁**原文 ——「**若 H1/H2/H3 反转 ⇒ B1 返工走升版**」。
而 H1/H2/H3 **此前从未判决**（Round 1 只判 H4/H5/H8/H9/H10，三者属 Round 2）⇒ 本轮 **H1 判否属「首判」**，**不满足「反转」** ⇒ **门禁不触发**。

🔴 **反模式**：把「**首判判否**」当「**反转**」⇒ **误触发返工**，把"第一次判出否"错当成"推翻了原判"。
🔴 **写门禁时的正解**：若确实希望「**首判即触发**」，须**显式写**成「**首次判决为否 ⇒ …**」，**不得**用「反转」兼指两种情形。

> **同族**：`§S2-a J-2④`「判据须显式写明**适用时点 / 前置条件**」—— 本条是「**条件词语义边界**」的补充。

### S5 · 总门禁（total_gate 必须机器可判）

🔴 **总门禁不得只写"全部通过"**，必须落成**校验脚本 + 退出码语义**：

| 件 | 要求 |
|:--|:--|
| 校准基线 | **单一声明锚点** —— 可数事实只在**一处**声明，校验器与文档均从它解析，**不写死数字** |
| 退出码 | 明确语义（如 `0 全绿 / 2 有漂移须修（不是警告）/ 3 环境错`） |
| 回归用例 | **4 类，缺 ⚪ 则无法区分"修好了"与"改瞎了"**：🟢现状 / 🔴真实坏样本 / 🔴注入坏样本 / **⚪真阴性（好样本不被误报）** |
| 端到端抽查 | **每批必做一次**（不只查各步日志）：挑一个已知应有值的对象，走完整链路 |

> 范本：某内部项目 `tools/kb_verify.py`（单一声明锚点 + 退码 0/2/3 + 4 类回归 4/4 通过）。
> 🔴 **"日志全绿 ≠ 链路通"** —— 各步日志全部"成功"而端到端为空的实例真实发生过（判据双源）。

### S6 · 复盘回流（人工版 `plan-auditor`）

| # | 复盘项 |
|:-:|:--|
| 1 | 预判正确项（判据必须是**先于执行**的文本，不能是任务书本体 —— 它已被就地改写） |

| 4 | 自指判据缺陷的模式 |
| 5 | 可固化为技能的清单（含"已固化/半固化/未固化"实测状态） |

#### 🆕 §S6-a · 复盘必须覆盖"记录之外"的缺陷（**2026-09-24 新增**）

⇒ **推论（重要）**：**任何"以后我会注意"式的结论都不可采信**；**只有加校验器才是出路**（记录 ≠ 拦截）。

#### 🆕 §S6-b · 作废项关闭时必须**同时留"反问"**（**2026-09-24 新增**）

🔴 **反模式 #13 的正解**：关闭任何对象/判据时，**必须同时留下"那接下来该问什么"**，否则即"完成即留尸"。

|:--|:--|

#### 🆕 §S6-c · 通用内核须**归位到跨领域技能**，不得只留在领域技能里（**2026-09-24 新增**）

- 判据：**把该结论的"形式"剥离后，剩下的原则是否与领域无关？** 若无关 ⇒ **必须归位跨领域技能**，领域技能**留指针**。
